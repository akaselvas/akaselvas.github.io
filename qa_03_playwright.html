01 — Project

Playwright E2E Automation Suite

A 24-file, 161-test end-to-end regression suite written in Playwright + TypeScript against Practice Software Testing (Toolshop) — an open-source Angular/Laravel/MariaDB e-commerce app purpose-built for QA practice. The scope covers the full customer journey (catalog, cart, checkout, payment), account security (registration, TOTP/2FA, password recovery, account locking), a conversational chat widget, geolocation and combination discounts, six-language i18n, and a full admin back office — closed with a self-hosted CI/CD pipeline in GitHub Actions.

This portfolio documents not just the final suite, but the actual debugging process behind it: the locator decisions that broke on translation, the strict-mode violations that each hid a different characteristic of the app, and the CI/CD pivot from testing a public site to containerizing the application itself inside the runner.

02 — System

The CI pipeline didn't start where it ended up. The first working version simply pointed Playwright at the public production site — and passed, mostly. A meaningful chunk of tests (60+, spanning invoicing, login, and i18n) failed intermittently, with no logical connection to the test code: elements that should exist simply weren't in the DOM. The fix wasn't a longer timeout. It was removing the external dependency entirely.

The pivot this diagram represents

The application under test ships its own docker-compose.yml — Angular, Laravel, and MariaDB as containerized services with predictable ports. Cloning and booting it inside the runner turned an unpredictable, third-party-controlled failure (Cloudflare's bot policy) into a fully controllable, deterministic one (container configuration) — which could then actually be debugged and fixed for good. The one detail easy to miss: it isn't enough to swap baseURL. Every spec also calls page.request directly against apiURL for setup — leaving that pointed at production would mean the UI runs locally while the data comes from a live database.

03 — Locator Strategy

Playwright's textbook locator priority is getByRole → getByLabel/getByText → getByTestId → CSS as a last resort. The first real architectural decision of the project showed that rule isn't absolute — it has to be checked against what the application actually does.

Why getByTestId won, most of the time

The app ships a language selector (EN/DE/ES/FR/NL/TR) with form labels translated via Transloco. getByLabel('First name') works in English and breaks silently the moment the browser's default language changes — even while the app itself works perfectly. getByTestId (configured via testIdAttribute: 'data-test') is immune to translation because the attribute never changes with locale. The suite standardized on getByTestId for most flows, reserving getByRole for elements with a stable accessible name (filter checkboxes, table columns, fixed-English buttons) and getByLabel only where locale is guaranteed fixed.

Never guess a selector

Every locator was validated against the real HTML — DevTools or the Angular source — never assumed from convention. The category page is the clearest example: rather than presuming the price slider from the overview page would also exist there, reading the Angular template confirmed <ngx-slider> is genuinely absent on /category/*. That's not a missing test — it's a documented product bug, asserted directly instead of silently skipped.

Assertion — documenting an absence, not assuming one 
// category.component.html has no <ngx-slider> — confirmed via source read,
// not assumed. The overview page has one; the category page does not.
await expect(page.getByRole('slider').first()).toHaveCount(0);
04 — Findings

Synchronization was, by far, the area that demanded the most investigation — because "flaky" isn't a root cause, it's a symptom, and each occurrence below traced back to a different one. The generic fix (raise the timeout) only ever solved a fraction of them.

1. Strict Mode, Case 1 — Ambiguous text between title and description

Symptom strict mode violation — resolved to 2 elements
Root cause Free-text search matched content in two different places
Fix pattern Scope the locator to a specific test-id, not free text

What broke: A test confirming a favorite was removed used page.getByText('Combination Pliers'). Playwright refused to act, reporting the locator resolved to two elements. Inspecting the card revealed the product name appeared both in <h5 data-test="product-name"> and inside <p data-test="product-description"> — the description text happened to contain the product name too.

The lesson: searching by free text is inherently risky when the full content of the page isn't fully known — the string can legitimately appear somewhere unexpected. Scoping to a specific data-test attribute removes the ambiguity at the source instead of patching around it.

View source — 14_favorits.spec.ts#L84

2. Strict Mode, Case 2 — The "fixed" .first() trap

Symptom False positive — test passes without proving anything
Root cause Locators are dynamic; .first() is re-evaluated on every call
Fix pattern Assert on element count, not on a stale reference

What broke: The obvious fix for a delete-item test looks like: grab the first card, click delete inside it, then assert that card is hidden. But Playwright locators are re-evaluated on every call — once card 1 is removed from the DOM, the old card 2 becomes the new "first card." An expect(firstCard).toBeHidden() written this way re-resolves the locator, finds whatever now occupies that position, sees it's visible... and fails to notice the real assertion was never proven.

The lesson: this is a dangerous kind of false positive — the test goes green without proving anything. The fix was to assert on the count of elements before and after the action, a claim about system state rather than about an element reference whose meaning can silently shift.

View source — 14_favorits.spec.ts#L84 Fix — count-based assertion instead of a stale reference 
const cartTotalLocator = page.getByTestId('cart-total');
const firstPriceLocator = page.getByTestId('line-price').first();
const secondPriceLocator = page.getByTestId('line-price').nth(1);
const firstPrice = parseFloat((await firstPriceLocator.innerText()).replace('$', ''));

await page.locator('.btn.btn-danger').nth(1).click();

// Not "the old card is hidden" — the count of surviving delete buttons.
await expect(page.locator('.btn.btn-danger')).toHaveCount(1, { timeout: 15000 });
await expect(cartTotalLocator).toHaveText('$' + firstPrice.toFixed(2));

3. Strict Mode, Case 3 — One CSS class, two table columns

Symptom strict mode violation — resolved to 2 elements
Root cause Same [ngClass] directive shared by unit-price and total columns
Fix pattern Understand the table structure, then decide deliberately which column

What broke: the product detail discount test used page.locator('span.discounted'), which resolved to two elements. Reading the HTML showed the discounted class was applied via the same Angular [ngClass] conditional to both the unit-price column and the total column.

The lesson: the fix wasn't tacking on .first() arbitrarily — it was understanding the table's structure and explicitly deciding, and documenting, which of the two columns the test actually needed to validate.

View source — 02_product-detail.spec.ts#L39

4. Strict Mode, Case 4 — Chat history that never clears

Symptom strict mode violation — resolved to 5 elements
Root cause Chat DOM is never cleared — every prior message stays mounted
Fix pattern Target .last() deliberately — the newest instance, not "the" instance

What broke: the chat widget's "Back to menu" button reappears at every conversation step, but the DOM is never cleaned up — every prior message stays on screen. In a longer support-ticket flow, getByTestId('chat-action-back-to-menu') resolved to five identical buttons at once. This was a UI behavior, not a badly written test.

The lesson: the fix here was the mirror image of Case 2 — deliberately targeting .last(), the newest element in the conversation, rather than assuming there'd only ever be one. Four cases, four different real characteristics of the app (duplicated text, shared CSS, cumulative UI history, positional drift) — no generic fix worked twice.

View source — 19_chat-widget.spec.ts#L212

5. A Typo, Not a Race — the cost of a manual network listener

Symptom Intermittent — edited row not always first after re-search
Root cause A typo ('QUERY' instead of 'GET') hid the real issue for a while; the underlying race is timing between the write and the search reflecting it
Status Open — mitigated via retry, not eliminated

What broke, first pass: editing and re-searching a product in the admin panel used page.waitForResponse(r => r.request().method() === 'QUERY' ...) — 'QUERY' isn't a valid HTTP method, it was a typo for 'GET', so the promise never resolved. Manually tracking a network listener across several searches in the same test turned out fragile on its own, independent of the app.

What's still true today: after replacing the manual listener with an auto-waiting assertion, the test is far more stable — but it still fails intermittently (about 1 in every few CI runs) with the edited row simply not present as the first row within the timeout window, which points to real timing between the write and the search index reflecting it, not a test bug:

View source — 18_admin-dashboard.spec.ts#L44 
// actual failure from a real CI run, kept here rather than hidden
                                                                Expected substring: "NewTooljpebhEdited"
                                                                unexpected value: "01KZ7T1JH3WF7RC07959QDGJGACombination Pliers23$14.15EditDelete"

The lesson: waiting for the right network response is necessary but not sufficient — the data returned still has to be checked against what the test expects. And just as important: when a test remains flaky after a genuine root-cause fix, the honest move is to say so explicitly rather than mark it green and move on. This one is tracked, not hidden — Playwright's retry currently absorbs it, and filtering the row by content instead of position is the next step being evaluated.

6. The Hidden Hammer — UI state differs between production and CI

Symptom Timeout on getByRole('checkbox', {name:'Hammer'}) — CI only
Root cause The Dockerized (Sprint 5) build starts the category tree collapsed
Fix pattern Expand the parent category before checking a child

What broke: a category-filter test that always passed against production started consistently timing out in CI, right after the pivot to Docker described in Section 2. The category tree in the sidebar of the local (Sprint 5) build starts collapsed by default, hiding the "Hammer" checkbox inside the closed "Hand Tools" parent. Playwright correctly refuses to interact with a hidden element and burned through the 30s timeout waiting for it to appear.

The real lesson: not the one-line fix itself, but the diagnostic method — a Playwright timeout almost always points to a real, verifiable state of the application (hidden, disabled, or off-screen), never to a random framework bug. The correct move is comparing the two environments structurally before touching the test.

View source — 01_product-overview.spec.ts#L77 Fix — expand the parent before checking the child 
await page.getByRole('checkbox', { name: 'Hand Tools' }).click(); // expands the tree
await page.getByRole('checkbox', { name: 'Hammer' }).check();

7. TOTP Clock Drift — The hardest bug to reproduce on demand

Symptom Intermittent "Invalid TOTP" on otherwise-correct codes
Root cause TOTP is time-window based; local clock vs. server clock drift
Fix pattern Derive an offset from the API's own Date header, generate codes against it

What broke: TOTP codes generated with the otpauth library (SHA1, 6 digits, 30s period) from the app's own exposed secret (data-test="totp-secret") failed verification intermittently — a few seconds of drift between the test machine's clock and the server's is enough to land in the wrong 30-second window.

The fix: read the Date HTTP header returned by the API on user registration, compute a timeOffset, and generate every subsequent code against Date.now() + timeOffset instead of the local clock. Low frequency, high cost to debug — it doesn't reproduce on the first try, which made it one of the most expensive bugs in the whole suite to pin down.

View source — 11_topt.spec.ts#L83 Fix — sync to server time before generating a code 
let timeOffset = 0;

const serverDateHeader = registerResponse.headers()['date'];
if (serverDateHeader) {
    timeOffset = new Date(serverDateHeader).getTime() - Date.now();
}

function generateTOTP(secret: string): string {
    const adjustedTime = Date.now() + timeOffset;
    const totp = new OTPAuth.TOTP({
        secret: OTPAuth.Secret.fromBase32(secret),
        digits: 6, algorithm: 'SHA1', period: 30,
    });
    return totp.generate({ timestamp: adjustedTime });
}
05 — Test Plan Scope

The 24 spec files map to eight functional domains of the application. Every test is named and tagged (@sprint5, @AC1, @AC2...) 1:1 to a functional acceptance criterion, with the matching Given/When/Then as a comment at the top of the test body — allowing execution to be filtered by criterion (--grep @AC5) with a report that traces directly back to a requirement.

Requirements traceability, not assumption

Every acceptance criterion tagged above comes from the project's own published Sprint 5 user stories — not from reverse-engineering the UI. That mattered in both directions. Error message wording was preserved verbatim even where the spec itself has a grammatical slip ("Your current password does not matches with the password."), because "correcting" it would mean asserting against text the app never actually shows. And where the spec and the shipped app disagree — AC1 of the Contact Form calls for a "Known user, [Full Name]" message, but the deployed app actually renders "Hello Jane Doe, please fill out..." — the test asserts against what the application actually does, with the discrepancy documented rather than silently reconciled to match the doc.

Domain 1 — Catalog & Product Discovery 3 files · 33 tests

Files: 01_product-overview, 02_product-detail, 03_rental_products.

  • Overview grid: card content (image, name, price), search with active-filter reset, category and brand checkboxes, hierarchical parent/child category selection, sorting (name/price, both directions), the price range slider (default $1–$100, max $200) driven by simulated mouse drag and keyboard arrow input, and discount/out-of-stock badges.
  • Product detail: quantity selector clamped between 1 and 999,999,999, add-to-cart success messaging, out-of-stock disabling the button, favorites (add / duplicate / unauthorized), and related products.
  • Rentals: the duration slider (1–10 hours, keyboard-driven for determinism) and the assertion total = hourly_rate × duration, recomputed from the DOM rather than hardcoded.

Domain 2 — Checkout Flow 4 files · 24 tests

Files: 04_checkout-cart, 05_checkout-signIn, 06_checkout-address, 07_checkout-payment.

  • Cart: quantity recalculation derived mathematically from the read unit price (never a hardcoded expected value), item deletion with count-based assertions (Finding 2), empty-cart state, and the 15% discount badge/subtotal/total math on discounted items.
  • Sign-in step: guest login form, and full TOTP-gated login reproduced end-to-end during checkout — register, enable 2FA, log out, add to cart, and log back in through the checkout wizard with a live TOTP code.
  • Address: field length limits against Angular's ng-invalid class, required-field validation disabling "Proceed", and a real postcode-lookup flow (NL/1011AB) used specifically to satisfy backend address validation for the order-placement test.
  • Payment: all five payment methods and their field sets, credit card expiration-date validation, and a documented UI race condition in the "Confirm" button (see Section 6) reproduced faithfully with two sequential clicks rather than masked.

Domain 3 — Authentication & Account Security 6 files · 38 tests

Files: 08_user-registration, 09_user-login, 10_forgot-password, 11_topt, 12_profile, 13_change-password.

  • Registration & password strength: all required fields, real-time password requirement feedback, and the 5-level strength indicator (Weak → Excellent), reused between registration and password change — the latter needed a manual dispatchEvent('input') to work around an updateOn: 'blur' delay.
  • Login: role-based redirect (customer vs. admin), invalid credentials, account locking after 3 failed attempts (HTTP 423 + message), admin exemption from locking, disabled-account rejection (HTTP 403), and Google OAuth popup validation (domain, callback route, window dimensions) without authenticating against the real provider.
  • TOTP: full setup lifecycle — QR code, manual secret, verification, invalid code — plus the server-clock-sync fix from Finding 7, and the business rule denying TOTP setup to the two shared demo accounts.
  • Profile & password change: editable vs. read-only fields, successful updates with fade-out confirmation, password-mismatch and current-password-verification errors, and forced logout after a successful password change.

Domain 4 — Personalization 2 files · 5 tests

Files: 14_favorits, 24_browse-by-category.

  • Favorites: the list is seeded entirely via API (register → login → /favorites) rather than clicking through the UI three times, keeping the test focused on the favorites page itself; empty state and removal are covered separately.
  • Category browsing: confirms the category page shares category/brand filters, sorting, and pagination with the overview — but explicitly documents that the price slider does not exist there (see Section 3).

Domain 5 — Post-Purchase & Support 3 files · 19 tests

Files: 15_invoices-pdf, 16_messages, 17_contact-form.

  • Invoices: generated PDF invoices tied to real orders, validated for presence and identifying data rather than pixel content.
  • Messages: a paginated table (subject, message truncated to 50 chars, status badge, date, details link), chronological reply ordering verified by comparing two real timestamps, and posting a reply through the UI with a live network-response wait.
  • Contact form: auto-fill and field-hiding for logged-in users, guest-required-field validation, the 50-character minimum message rule, and the unusual file-attachment rule — .txt only, and the file must be exactly 0 KB — tested with in-memory buffers instead of versioned fixture files.

Domain 6 — Admin Operations 1 file · 9 tests

File: 18_admin-dashboard.

  • Dashboard: the sales chart canvas and the paginated recent-invoices table.
  • Full CRUD suites: products, categories, and brands each follow the same add → search → edit → search → delete lifecycle in the UI, with unique randomized names to avoid collisions between parallel or repeated runs. Users are seeded via API and then edited/deleted through the UI.
  • Order management: status dropdown values (AWAITING_FULFILLMENT → COMPLETED) and the order-edit detail sections.
  • Account enable/disable: toggling a user's enabled flag from the admin panel and confirming, in a second browser context logged in as that customer, that login is actually blocked and later restored — a real cross-session effect, not just a UI checkbox state.
  • Reports: monthly/weekly sales charts and the statistics page's four breakdown panels.

Domain 7 — Conversational & Discount Engine 3 files · 22 tests

Files: 19_chat-widget, 20_geo-location-discount, 21_combination-discount.

  • Chat widget: the menu (Find Product / Order Product / Checkout / Support), product search returning up to 5 result cards, a full order-to-cart flow with quantity selection, and an entire checkout wizard re-implemented conversationally — cart summary → address → payment → confirmation, driven step-by-step as a state machine where every bot reply is confirmed by content before the next input is sent. The invoice endpoint was mocked via page.route() to isolate the chat flow from backend postcode-lookup validation. The empty-cart scenario is a documented test.fixme — it exposes a real JS exception (TypeError: reading cart_items of null).
  • Geo-location discount: five cities × five discount tiers (5%–25%), plus a neutral/unsupported-location case, all driven by mocked GEO_LOCATION coordinates in localStorage injected via page.addInitScript before the page loads.
  • Combination discount: the 15% cart-wide discount that appears only when a rental item and a non-rental item share a cart, validated on the cart page and re-validated against a real invoice created via API, with the discount removed and reverted when the mixed-cart condition no longer holds.

Domain 8 — Compliance & Internationalization 2 files · 11 tests

Files: 22_multi-language, 23_privacy-policy.

  • i18n: automatic browser-language detection for all 6 supported languages via test.use({ locale }), fallback to English for unsupported locales, manual switching through the UI selector, and — critically — persistence: a manually chosen language must survive a page reload and outrank automatic detection on the next visit.
  • Privacy policy: presence of every required disclosure topic (Google Sign-In, data collection, hourly automatic removal, third-party services, data security, contact info).
06 — CI/CD Journey

The final workflow doesn't run npx playwright test against a URL — it builds the thing it's testing, from source, inside the runner, every time. Eleven sequential steps, each added to solve a problem the previous version actually hit in practice.

Steps 1–2
Checkout & clone SUT
Checks out the test repo, then clones the application's real source — testing against current product code, not a frozen image.
Steps 3–4
Configure & boot
Forces production: true, injects dummy Google OAuth creds so the build doesn't fail on a missing var, then docker compose up --build --force-recreate.
Steps 5–6
Container plumbing
Fixes bootstrap/cache / storage permissions on the fresh Laravel container, then installs Composer dependencies inside it.
Steps 7–9
Health checks & seed
Active polling loops (mysqladmin ping, then curl for API and UI) instead of a fixed sleep, then migrate:fresh --seed and a background queue worker.
Steps 10–11
Test & report
Runs the Chromium project with URL/API_URL pointed at localhost, and uploads the HTML report as an artifact even on failure.

07 — Automation Approach

Hybrid testing — API for setup, UI for validation

page.request prepares state directly through the API whenever a test only needs a state, not a validated journey to reach it: user registration and login tokens, seeding a cart or favorites list, creating full invoices to test the invoice display page in isolation, and elevating to an admin session to flip a user's enabled flag for edge-case testing. page.route() is used sparingly, to mock the invoice endpoint during the chat-widget checkout flow — isolating that specific UI journey from an unrelated backend postcode-lookup dependency.

Data isolation between tests

Any test that mutates user state (password, TOTP, account locking, favorites) creates its own account via API with a unique email (user-${Date.now()}@example.com), never reusing a fixed account for anything destructive. The two shared demo accounts (customer@..., admin@...) are reserved for read-only or non-destructive scenarios — avoiding the classic "one test breaks the next" failure caused by execution-order dependency.

Business-rule math is never hardcoded when it can be derived: cart line totals are recomputed from the unit price read off the DOM, rental totals from hourly-rate × slider duration, and the 15% combination discount is checked with floating-point tolerance (toBeCloseTo) against a subtotal read from the page itself — making every one of those assertions resilient to price or seed-data changes between runs.

Documenting known bugs instead of hiding them

Two confirmed application defects — the pre-fill of a logged-in user's address at checkout, and a JavaScript exception when starting chat checkout with an empty cart — are kept in the suite as test.fixme(true, 'reason') rather than deleted. The test's intent and expected assertion stay in the codebase and visible in every run's output, without breaking the pipeline. A third defect — a real payment-confirmation race condition, where the first click only "warms up" internal state and only the second click actually creates the order — wasn't masked either: the test reproduces the exact two-click behavior with two sequential, distinct waitForResponse calls, proving the real user flow instead of hiding the bug behind an artificial workaround.

08 — The Engineer

From Design to Quality Assurance

My background is in design and visual communication, which taught me to look closely at what's actually happening on screen instead of what's supposed to happen. That instinct carried over directly into test automation — the strict-mode violations in Section 4 weren't solved by reading Playwright documentation harder; they were solved by reading the application's real HTML and asking why a locator found more than one thing.

I'm transitioning into Software Quality Assurance because I want the paranoia for edge cases and the discipline of a regression net that a designer's eye alone doesn't give you. This suite — 24 files, 161 tests, and a CI pipeline that had to be rebuilt from the ground up once — is one month of learning Playwright by hitting real failures and diagnosing them one at a time, not by following a tutorial to a green checkmark.
