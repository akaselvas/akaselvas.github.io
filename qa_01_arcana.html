02 — System

Architectural Threat Map: Out of nearly 40 defects identified during the 340-point QA audit, these five represent the most critical and structurally diverse vulnerabilities. They span across five distinct architectural layers: two inside Flask's runtime (memory mutation, template injection), one at the proxy boundary (IP spoofing), and two on the WebSocket channel, one inbound (hijacking), one outbound (dead SID).

03 — Strategy

I structured the QA process using a professional Scrum hierarchy: 9 Epics and 54 User Stories, decomposed into a rigorous matrix of over 340 executable subtasks tracked in Jira. I deliberately prioritized manual testing for this phase because automation only verifies what it is scripted to check. Manual exploratory testing brings the intuition and flexibility needed to uncover hidden bugs, unpredictable edge cases, and usability issues that fall outside of rigid automated paths.

When transitioning to automation, I applied a strict triage filter based on a single guiding question: "If this breaks, will the app crash, get hacked, or cost me money?." Visual and animation validations remained manual, while critical security gates, API quota protections and core routing logic were translated into a Pytest suite. This created a permanent regression safety net, ensuring that applying complex fixes during the QA phase never broke previously verified behavior.

Result: A test plan of 340 subtasks in Jira, backed by over 100 automated tests integrated into GitHub Actions for continuous CI/CD validation.

04 — Findings

Selected from nearly 40 identified defects, these findings showcase the intersection of security auditing and systems engineering. Each entry follows a rigorous documentation standard: defining the observable failure, analyzing the real-world impact on API resources or user data, and verifying the fix through targeted regression testing to ensure long-term stability.

1. Global Deck Mutation — Concurrency & Data Corruption

Severity Critical — Silent data corruption
Ref AF-62
Method Source review of global state + concurrent request simulation

What broke: The shuffle function mutated TAROT_CARDS dicts in-place — writing card["value"] = "invertido" directly onto objects in the global list. Under gevent's concurrent model, this list lives in process memory for the entire server lifetime.

Real-world impact: Request A starts writing orientations to the global list while Request B is halfway through reading them. The global deck becomes a shared mutable scratchpad — the last concurrent write wins. After the first request, the deck is never truly random again; every subsequent reading inherits leftover orientation state from whoever hit the server last. The app logs zero errors, returns HTTP 200, and appears completely healthy while producing subtly incorrect results on every request under load.

The fix: deck_copy = [card.copy() for card in TAROT_CARDS] — shuffle and mutate the copy, never the global variable.

Regression test — verify global immutability 
def test_global_deck_not_mutated(client):
    """The global TAROT_CARDS list must remain pristine across requests."""
    with client.session_transaction() as sess:
        sess["selected_cards"] = "3"
 
    client.get("/cartas")  # Triggers shuffle and orientation assignment
 
    # Hard assertion: no card in the global list should carry a value after the request
    from app import TAROT_CARDS
    for card in TAROT_CARDS:
        assert "value" not in card, (
            f"Global card '{card['name']}' was mutated! Concurrency risk detected."
        )

2. Rate Limiter Bypass — X-Forwarded-For IP Spoofing

Severity Critical — Infrastructure / DoS
Ref AF-185
Method Header inspection + ProxyFix misconfiguration analysis

What broke: Two separate failure modes existed depending on the ProxyFix configuration. Without it, Flask-Limiter received the load balancer IP for every user. With x_for set too high, an attacker could prepend a fake IP to X-Forwarded-For and bypass the rate limiter entirely.

Real-world impact: In the misconfigured state, all 400+ daily users shared a single rate counter keyed to Render's load balancer IP. Any one user exhausting the daily limit would trigger a 429 that blocked every other user simultaneously. In the over-trusted state, a single attacker header (X-Forwarded-For: 127.0.0.1) made the rate limiter read localhost as the client — giving unlimited free AI readings and draining Gemini API quota.

The fix: ProxyFix(app.wsgi_app, x_for=1, x_proto=1, x_host=1, x_prefix=1) — x_for=1 exactly matches Render's single-hop architecture and closes both failure modes.

Regression test — two failure modes, two functions 
from flask_limiter.util import get_remote_address
 
def test_rate_limiter_keys_to_client_ip_not_load_balancer(client):
    """Flask-Limiter must resolve the real client IP, not the proxy IP."""
    with client.application.test_request_context(
        headers={"X-Forwarded-For": "203.0.113.42, 10.0.0.1"}
    ):
        resolved = get_remote_address()
 
    assert resolved == "203.0.113.42", (
        f"Expected real client IP, got '{resolved}' — ProxyFix x_for misconfigured"
    )
 
def test_spoofed_forwarded_for_is_not_trusted(client):
    """With x_for > 1, an attacker header bypasses rate limiting."""
    with client.application.test_request_context(
        headers={"X-Forwarded-For": "127.0.0.1, 203.0.113.42, 10.0.0.1"}
    ):
        resolved = get_remote_address()
 
    assert resolved != "127.0.0.1", (
        "Spoofed localhost IP was trusted — x_for set too high"
    )

3. Cross-Site WebSocket Hijacking (CSWSH)

Severity Critical — API Security / Quota Theft
Ref AF-307 · AF-308 · AF-310
Method External domain Socket.IO injection

What broke: The @socketio.on('send_message') handler called no validate_csrf(), and the server was configured with cors_allowed_origins="*". Flask-Limiter is blind to WebSocket events entirely — HTTP rate limits do not apply to socket handlers.

Real-world impact: Any attacker page could get a logged-in user to visit it, establish a WebSocket connection using the victim's valid session cookie, and loop 200+ send_message events unimpeded. Every event triggers a Gemini API call at real cost. Testing confirmed that a 200-event loop completed without a single rejection.

The fix: validate_csrf() added to the handler plus a custom Redis-backed sliding window limiter — 10 messages per 60 seconds per session — because Flask-Limiter cannot be applied to socket events.

Regression test — verify socket event authentication 
def test_send_message_rejected_without_valid_csrf(socketio_client):
    """send_message must validate the CSRF token on every emit.
    Without this, any cross-origin page can drain Gemini quota."""
    received = []
    socketio_client.on("generation_error", lambda data: received.append(data))
 
    # Emit with a tampered CSRF token
    socketio_client.emit("send_message", {
        "message":      "test",
        "tarot_reading": "",
        "csrf_token":    "invalid-token-xyz",
    })
 
    assert len(received) > 0, "No error emitted — CSRF not validated on socket handler"
    assert "csrf" in received[0].get("message", "").lower()

4. JS Context Breakout — Template Injection Beats the Sanitizer

Severity Critical — Security depth / sanitizer blind spot
Ref AF-29
Method results.html source review + JS context payload testing

What broke: The intention field was interpolated raw into a socket.emit() call inside a <script> block: intencao: "{{ intencao }}". The server ran bleach.clean() on input, which appeared to sanitize it.

Real-world impact: bleach sanitizes HTML context — it strips <script> tags and encodes angle brackets. It deliberately leaves quotes and backslashes untouched because those are valid in text content. A user typing ", csrf_token: "anything" passes bleach cleanly, gets stored in the session, and Jinja2 injects it raw into a JavaScript string — breaking out and overwriting the CSRF token in the socket payload. With a more crafted payload ("}); maliciousFunction(); //), arbitrary code executes inside the CSP nonce boundary. The vulnerability is not in the HTML output pipeline at all — no amount of HTML sanitization ever catches it.

The fix: intencao: {{ intencao | tojson }} — | tojson JSON-encodes the string including all quotes, closing the injection point entirely.

Regression test — verify JS context escaping 
@pytest.mark.parametrize("payload", [
    '\", csrf_token: \"injected',
    '"}); maliciousFunction(); //',
])
def test_intencao_is_json_encoded_in_script_context(client, payload):
    """| tojson must be applied in results.html — bleach.clean() does NOT
    protect against JS context breakout."""
    with client.session_transaction() as sess:
        sess["intencao"] = payload
 
    html = client.get("/results").data.decode()
 
    # Raw payload must never appear verbatim inside a script block
    assert payload not in html, (
        f"Raw payload in rendered HTML — | tojson not applied: {payload}"
    )
    # JSON-encoded form must be present instead
    import json
    assert json.dumps(payload) in html

5. Dead SID — Infinite Loading Loop & Silent Quota Burn

Severity High — Silent money burn / async architecture
Ref AF-116
Method Network throttling / Wi-Fi disconnect simulation

What broke: In a Flask-SocketIO + Flask-Session stack there are two completely different things called "session". The code targeted socketio.emit() using session.sid as the room name — but session.sid is the Redis key from the HTTP session, not the socket's ephemeral per-connection room ID (request.sid). The emit fired at a room that doesn't exist.

Real-world impact: The Gemini API call completed successfully — consuming a real paid token. The result was emitted to a dead room. The client's loading spinner ran for 120 seconds, then the reconnection system retried up to 5 times, burning 5 more API tokens per stuck user. Zero errors in the logs, zero 500s, no indication anything was wrong. In a traffic spike this is silent, compounding quota burn: every concurrent stuck user costs 5 Gemini calls and receives nothing.

The fix: Replace session.sid with request.sid inside all @socketio.on() handlers — request.sid is the actual socket connection room ID. To survive network drops, the reading is now cached in Redis using the persistent Flask Session ID, allowing reconnected clients to retrieve it instantly.

Regression test — verify socket routing 
def test_generation_emit_targets_socket_room_not_redis_key(socketio_client, mocker):
    """socketio.emit() must target request.sid (the socket room),
    not session.sid (the Redis session key). Emitting to the Redis key
    sends the response to a room that does not exist."""
    emitted_rooms = []
    original_emit = socketio_client.application.extensions["socketio"].emit
 
    def capture_emit(*args, **kwargs):
        emitted_rooms.append(kwargs.get("to") or kwargs.get("room"))
        return original_emit(*args, **kwargs)
 
    mocker.patch.object(socketio_client.application.extensions["socketio"],
                        "emit", side_effect=capture_emit)
 
    socket_room_id = socketio_client.sid  # the real ephemeral room ID
    socketio_client.emit("start_generation", {"intencao": "test"})
 
    assert socket_room_id in emitted_rooms, (
        f"Emit targeted '{emitted_rooms}' — expected socket room '{socket_room_id}'. "
        "session.sid (Redis key) was used instead of request.sid."
    )
05 — Test Plan Scope

The 340+ manual test cases were organized into 9 Epics and 54 User Stories, mapped directly to the application's architecture. Each Epic targeted a distinct layer of the stack — from HTTP form handling to Redis session storage, WebSocket events, AI prompt integrity, and browser accessibility. A consistent triage filter was applied to automation decisions throughout: "If this breaks, will the app crash, get hacked, or cost money?"

Epic 1 — User Onboarding & Session Initialization 7 Stories

Focus: Every interaction before the user reaches the card board — form submission, backend validation, session initialization, and CSRF protection.

  • Happy Path & Validation: Testing all three valid card counts (1, 3, 5), the optional intention field, and verifying the backend correctly stores both values as strings in the Redis session — a type that the downstream card-limit logic depends on strictly.
  • XSS Sanitization (8 subtasks): Systematically testing bleach.clean() against script tags, img onerror handlers, malformed HTML, link injection, and the JavaScript quote-breakout vector. One subtask confirmed a vulnerability where Jinja2's standard rendering (without the | tojson filter) allowed double quotes to break out of the inline JS string literal in results.html.
  • CSRF Protection (9 subtasks): Verifying the full lifecycle — valid token baseline, missing token rejection, tampered token rejection, auto-reload on expiry, and the edge case where CSRF and session timers drift apart (CSRF at 1 min, session at 30 min). All tested on production.
  • Intention Length Limit: Boundary testing at exactly 400 and 401 characters, plus documenting the sanitization-before-length-check edge case where special characters like & expand to & after bleach processing, causing a 400-character input to exceed the limit.
  • Type Coercion Safety: Verifying that session['selected_cards'] is stored as a Python string (required for the not in ['1','3','5'] validation), while Jinja2 injects it into the JS template as a bare integer (required for the === strict equality counter logic). A type mismatch in either direction silently breaks the entire card selection flow.

Epic 2 — Card Selection & State Management 6 Stories

Focus: The card board's JavaScript state machine — from initial render to selection locking, animation timing, DOM reparenting, and final data serialization.

  • Shuffle & Orientation: Verifying that random.sample produces a different card order across sessions and that every card receives exactly one data-value attribute ("normal" or "invertido"). A key regression guard targets the deck_copy = [card.copy() for card in TAROT_CARDS] line — if removed, the global deck dictionary accumulates stale orientation values across concurrent users.
  • Selection Counter Logic: The entire card limit enforcement depends on a single Jinja2 injection: const selectedCardsCount = {{ selected_cards }};. If this renders as 0 or None, the condition clickedCards >= 0 is true on page load and no card can ever be clicked — with no visible error.
  • Double-Click & Race Conditions: Testing the card.dataset.processing = "true" lock against rapid double-clicks during the 333ms mid-flip window, and verifying the card.classList.contains('clicked') guard prevents re-selection after animation completes.
  • DOM Reparenting & Stage Transition: Verifying that stage.appendChild(card) physically moves the correct elements to #selection-stage, that the correct layout class (stage-1, stage-3, or stage-5) is applied, and that card orientations survive the transition unchanged.
  • Data Serialization & Backend Resilience: Testing the dynamic form construction in leituraButton.click, including CSRF token inclusion and backend handling of malformed, structurally invalid, and empty JSON payloads — each a separate crash or cost vector.

Epic 3 — AI Reading Generation (WebSocket Reliability) 4 Stories

Focus: The AI generation pipeline — from WebSocket event to Gemini API call to rendered HTML — and its failure modes.

  • Prompt Integrity: Using mocked model.generate_content calls to intercept and inspect the exact prompt string sent to Gemini, verifying that card names, orientations ("invertido"), and the user's intention all appear before the API is called. A missing card name means a wasted API call and a hallucinated reading.
  • Markdown Pipeline (Confirmed Vulnerability): Testing markdown_to_html() revealed that Markup() marks output as Jinja2-safe but performs no sanitization. The Python markdown library passes raw HTML through unchanged. If Gemini returns a <script> tag (via prompt injection), it survives the pipeline and executes via .innerHTML in the browser. This was documented as a confirmed finding with a recommended fix: pipe through bleach.clean() before wrapping in Markup().
  • API Failure Handling: Verifying that generate_tarot_reading() propagates exceptions — rather than swallowing them — so the background_generate task can emit generation_error to the client. A function that catches and returns None on failure causes a TypeError in the browser when it tries to inject None into the DOM.
  • Empty API Response: Confirming the explicit guard if not response.text: raise ValueError() catches safety-filter rejections, where the API returns a response object but with no text content.

Epic 4 — Contextual Chat (Interactive AI) 8 Stories

Focus: The chat interface as a separate runtime layer — its initialization, real-time feedback loop, security surface, and known architectural bugs.

  • Dead Code Discovery: Code review identified that initializeSocket() — the function registering all chat UI event listeners — was defined but never called. Only initSocket() was wired to DOMContentLoaded. If deployed, the chat button, close button, scroll shadow, and receive_message handler would all be silently inert. Documented as a critical dead-code bug.
  • WebSocket Payload Gaps (Confirmed Bugs): Two security bugs found via source inspection: handle_message used data['message'] (direct key access) instead of data.get('message', ''), meaning a missing key raises an unhandled KeyError in the gevent greenlet; and no message length limit existed before model.generate_content(), allowing unlimited-length chat prompts to reach the AI.
  • Loading Indicator Bug: removeLoadingIndicator() targeted .chat-message:last-child. If the user sent a second message before the first reply arrived, their second message bubble became last-child, and the first loading bubble was permanently orphaned in the chat history. Documented with a specific fix: use a unique class on the loading element and target it directly.
  • API Failure in Chat: Testing the background_chat exception handler via mocked API failures to verify a receive_message event is emitted on failure. If the except block silently fails, the client's loading indicator spins indefinitely with no recovery path.
  • Chat Rate Limiting: Verifying the in-memory sliding-window rate limiter (is_rate_limited()) exists and is called from handle_message — since Flask-Limiter's @limiter.limit decorator applies only to HTTP routes and cannot protect Socket.IO event handlers.

Epic 5 — Security, Performance & Infrastructure 6 Stories

Focus: The application's operational security layer — rate limiting, session hygiene, CSP enforcement, WebSocket authentication, and concurrent user isolation.

  • IP-Based Rate Limiting: Verifying Flask-Limiter's @limiter.limit decorator on /results returns a 429 after the configured threshold. The development limit is 200/min; production is 5/min, dynamically selected via the is_production flag.
  • Session Cookie Security: Asserting all three security flags in the Set-Cookie header: HttpOnly (blocks document.cookie access), SameSite=Lax (restricts cross-site POST), and Secure (HTTPS-only in production, HTTP-accessible in dev). The Secure flag is dynamically tied to is_production — hardcoding either value in either direction is a bug.
  • WebSocket CSRF (Manual Attack Simulation): Manually emitting start_generation with a missing token, a forged token, and confirming the server emits generation_error in each case. Tested on production via browser console injection.
  • Data Isolation (Concurrent Users): Running two independent test clients against /process_form simultaneously to verify session data (intencao, selected_cards) is keyed per-session-ID in Redis and cannot leak between users. Also testing the same-browser concurrent-tab race condition on session['selected_cards'] writes.
  • Session Expiry: Testing that the SESSION_PERMANENT=False setting produces a cookie with no Expires or Max-Age attribute — making it a true browser-session cookie that disappears on close, critical for shared-device privacy.

Epic 6 — Responsive Design & Device Compatibility 4 Stories

Focus: Mobile-specific rendering behavior, touch event semantics, and the tab-privacy mechanism introduced to handle shared-device use cases.

  • Orientation Lock: Testing the #rotate-message overlay controlled by a CSS @media (orientation: landscape) rule, verifying it blocks interaction in landscape and disappears instantly on rotation.
  • Mobile Keyboard Handling: Testing the isTouchDevice() detection via window.matchMedia("(hover: none) and (pointer: coarse)"), the keyboard-active class applied to <body> on input focus, and the scrollIntoView behavior that prevents the keyboard from covering the textarea. Also verifying the localhost exclusion so the behavior doesn't trigger during local development.
  • Touch Event Compatibility: Verifying that standard click event listeners fire immediately on mobile tap without legacy 300ms delay (suppressed by the width=device-width viewport meta tag), and that CSS :hover states don't persist after tap-and-release ("sticky hover").
  • Tab Privacy Guard: The /clear_session route, introduced to support the sessionStorage-based tab detection in cartas.html and results.html, was specifically security-audited: verifying it is @csrf.exempt (required because the JS fires before any token is available), accepts only POST, fully clears all session keys, and returns JSON — each a distinct crash or data-breach vector if broken.

Epic 7 — Navigation, Session Guards & Error Handling 7 Stories

Focus: Out-of-order navigation, infrastructure outages, and the application's behavior when users don't follow the intended linear flow.

  • Session Guard Bug (Confirmed, Fixed): The original /cartas route used int(session.get('selected_cards', 0)), which defaulted to 0 on missing sessions. The page rendered with HTTP 200, but selectedCardsCount = 0 made clickedCards >= 0 immediately true — no card could be clicked, with no visible error. The fix (if raw_val not in ['1','3','5']: redirect) was regression-guarded with parametrized tests covering eight distinct invalid session values.
  • Direct URL Navigation: Testing all three routes (/, /cartas, /results) with no session, partial sessions, and expired sessions to verify correct redirect chains without any route serving a 500 or a broken 200.
  • Bfcache & Browser Back: Documenting state desynchronization when navigating back from /results to /cartas via the browser's Back button — the DOM retains flipped cards but the JS clickedCards counter resets to 0, potentially allowing the user to exceed their original card limit.
  • 404 Handler: The custom @app.errorhandler(404) redirects all app routes to home (leaking nothing) but passes static file requests through as real 404s. Both code paths were tested separately, and Talisman security header presence was verified on both response types.
  • Redis Outage: Simulating Redis unavailability to verify the application does not leak stack traces or environment variables. Documenting that Flask-Limiter fails open by default during outages — allowing unrestricted traffic — which was logged as a risk item.

Epic 8 — Security: Headers, CORS & Dev Leaks 7 Stories

Focus: Attack surfaces not covered by Epic 5 — Talisman's default security headers, WebSocket CORS policy, CSP nonce configuration, and development tooling leaks.

  • Talisman Security Headers: Verifying X-Frame-Options: SAMEORIGIN (clickjacking), X-Content-Type-Options: nosniff (MIME sniffing), and Referrer-Policy across all routes and both error-response code paths (the redirect-based 404 and the pass-through static-file 404).
  • CORS Wildcard (Confirmed Vulnerability): cors_allowed_origins="*" was hardcoded unconditionally in the original code, allowing any external website to establish a WebSocket connection. Combined with the missing CSRF on send_message, this created a confirmed Cross-Site WebSocket Hijacking (CSWSH) exploit path where an attacker's page could silently consume Gemini API quota for free. Documented with a specific fix: restrict to the production domain conditionally via is_production.
  • CSP Nonce Misconfiguration (Confirmed Vulnerability): g.nonce was generated on every request and applied to script tags, but Talisman was not initialized with content_security_policy_nonce_in=['script-src'], and 'unsafe-inline' remained in script-src. The nonce was cosmetic — the browser ignored it entirely because unsafe-inline unconditionally allows all inline scripts. Any XSS injection point would execute without restriction.
  • send_message CSRF Gap (Confirmed Vulnerability): handle_generation called validate_csrf(); handle_message did not. An authenticated WebSocket connection could send unlimited chat prompts directly to the Gemini API without any token. Documented with exact code changes required for both backend and frontend.
  • Development URL Leak in Production CSP: The if not is_production: guard wrapping localhost and LAN IP entries in the CSP dict was verified via source inspection — an inverted or missing condition would whitelist http://localhost:3000 in the production CSP, creating a potential SSRF-based CSP bypass surface.

Epic 9 — Reliability, Cross-Browser & Accessibility 5 Stories · Manual Only

Focus: Scenarios that require a live browser, real devices, or human judgment — WebSocket network resilience, cross-browser rendering parity, keyboard accessibility, screen reader compatibility, and performance benchmarking. Not automated; executed manually on production via BrowserStack and Chrome DevTools.

  • WebSocket Resilience: Simulating hard network drops mid-generation using Chrome's Network Throttling panel. Found and confirmed a previous infinite-loading bug (since resolved via a reconnection architecture that emits cached readings on reconnect). One known architectural limitation was documented as Won't Fix: two tabs sharing the same browser session can receive cross-contaminated generation_complete events because SocketIO SIDs are per-connection, not per-session.
  • Cross-Browser Compatibility: Full end-to-end flow testing on Firefox, Safari (macOS), iOS Safari (via BrowserStack), and Edge. Verified CSS rotateX/rotateY transforms without vendor prefixes, Web Animations API (element.animate) support, WebSocket wss:// connection establishment, and marked.js rendering parity. All browsers passed without requiring polyfills.
  • Keyboard Navigation & Accessibility Bugs Fixed: Full Tab-order audit across all three pages and the chat modal. Found that the Escape key did not dismiss the chat overlay — fixed by adding a global keydown listener. Found that keyboard focus could escape the chat modal — fixed by implementing a focus trap that intercepts Tab and Shift+Tab and cycles within the modal boundaries.
  • Screen Reader & ARIA: All 22 card buttons were unlabeled (<button> with no text content), announced by screen readers as "button" with no context — fixed by adding dynamic aria-label attributes via Jinja2. The #loading-message lacked an ARIA live region, so screen readers received no notification when the AI finished generating — fixed by adding role="status" and aria-live="polite". Color contrast measured at 3.31:1 for inactive card buttons, meeting the WCAG AA UI component standard.
  • Performance Benchmarks: Established production SLA baselines: TTFB for / at 968ms (within 1000ms target), TTI for /cartas improved after a 46% asset size reduction (262KB PNG → 140KB WebP). AI reading generation averaged 5–9 seconds across 10 runs; chat responses averaged 3–5 seconds. Stress test with 5 concurrent users showed 63% average latency increase vs. baseline — documented as an acceptable degradation for the current single-instance deployment.
05 — Automation

What Pytest automated

Backend route behavior, session state integrity across requests, input sanitization reaching the AI prompt, CSRF token enforcement on all mutation endpoints, and WebSocket handler security via the Flask-SocketIO test client. Every test hits the actual application code—no mocks were used for the security assertions.

What was explicitly not automated

CSS transitions, animation timing, mobile viewport breakpoints, and orientation-based layout changes. These require a browser rendering engine and belong in Playwright or Cypress, not a unit test runner. Documenting this boundary is part of the strategy—pretending those cases don't exist would be a worse signal than the gap itself.

The xfail pattern (Test-Driven Bug Fixing)

Two known vulnerabilities—a KeyError crash in the WebSocket handler when a session key is missing, and an unbounded chat input with no API cost guard—were written as @pytest.mark.xfail tests before the fix was applied. This documented each vulnerability with a reproducible case that automatically converted to a passing test when the code was fixed. A test that starts red and goes green on the fix is a much stronger signal than a test written after the fact.

Transparency Note: The automated test code was written in collaboration with AI pair-programming tools. I designed the test strategy, identified the edge cases through manual exploratory testing, and reviewed all generated code against the application source. Utilizing AI assistance for test generation is a standard multiplier in modern professional QA workflows.
